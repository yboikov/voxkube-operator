Puppet, run by Kubernetes.

VoxKube is an operator for OpenVox, the community-maintained, open-source Puppet. Describe your Puppet server and the machines it manages in YAML; the operator runs the CA, the compilers and PuppetDB, deploys your code from Git, and keeps it all that way.

$ helm upgrade --install voxkube-operator \
    oci://ghcr.io/yboikov/charts/voxkube-operator \
    --namespace openvox --create-namespace

API v1alpha1: minor releases may still change it, always with upgrade notes. Every release candidate runs an end-to-end test on a live cluster before it ships.

What it takes care of

The parts of running Puppet that usually live in runbooks. Each links to the fields that control it.

Certificates

Runs the Puppet CA and approves machines your way: one by one through a VoxNode, with a pre-shared key, or by hand. Revocations reach the compilers through the synced CRL, and every certificate's expiry is a metric.

  • ca.autosignMode
  • ca.ttl
  • certificateNotAfter

Code

Deploys your control repo with g10k: every branch, or only the ones you list, becomes an environment. It signs in as a GitHub App, with an SSH key or a token, and polls instead of waiting for a webhook. Or ship code as an immutable OCI image.

  • code.mode
  • code.git.branches
  • code.git.authType

Secrets

Secrets from External Secrets Operator, or any Secret, become Hiera data for all machines, a role or one machine, always marked Sensitive. Certificates from cert-manager reach machines the same way. No eyaml keys to hand around.

  • hieraSecrets
  • certificates
  • secrets

Scale and uptime

Stateless compilers scale with a HorizontalPodAutoscaler, spread across nodes and keep a PodDisruptionBudget for drains. Probes give a cold JVM time to start. Hiera data is split across Secrets when it outgrows 1 MiB.

  • server.autoscaling
  • placement
  • hieraSecrets.shards

Monitoring

Machines found in OpenVox DB become Prometheus targets, labelled with their Puppet role. Failed runs, missed check-ins and expiring certificates are operator metrics, ready for your own alert rules.

  • selector
  • serviceMonitor
  • metrics

Operations

Everything is YAML you keep in Git and sync with Argo CD or Flux. Pods run under OpenShift's restricted-v2 without extra permissions. One annotation pauses a cluster during CA or database maintenance.

  • voxkube.io/paused
  • placement
  • upgrading

Three resources, one installation

Everything is configured through three custom resources. Each one is a YAML file you can keep in Git.

VoxClusterkubectl get vc
The Puppet server

Creates and runs the whole OpenVox stack: a CA, a pool of stateless compilers, OpenVox DB (PuppetDB) on your PostgreSQL, and your control repo deployed from Git. One per Puppet installation.

VoxNodekubectl get vn
One managed machine

Approves the machine's certificate and decides what Puppet applies to it. It can also hand the machine TLS certificates from cert-manager and secrets through Hiera, mute its alerts, and retire it cleanly.

VoxDiscoverykubectl get vd
Machines for Prometheus

Asks OpenVox DB which machines exist, for example every machine that runs profile::node_exporter, and publishes them as Prometheus targets with labels like their Puppet role.

How a machine joins

From a fresh VM to a monitored, configured machine, without logging in to the CA.

  1. The agent asks for a certificate

    The new machine sends a certificate request to the CA.

  2. A VoxNode appears

    The operator creates a VoxNode waiting for approval, unless you added one to Git first.

  3. You approve it

    Set state: Active and the machine's role. The operator signs the certificate.

  4. Puppet configures it

    The agent gets its catalog from the compilers, built from your Git code and the VoxNode's role.

  5. OpenVox DB knows it

    Facts and run reports land in PuppetDB; the VoxNode shows the last run.

  6. Prometheus scrapes it

    A VoxDiscovery picks the machine up and publishes it as a scrape target.

Made for OpenShift and GitOps

OpenShift Routes included

Every pod runs under the default restricted-v2 SCC. Turn on a Route and the operator creates a TLS-passthrough Route for the compilers or the CA, adds the hostname to the certificate and reports the URL agents should use. Agents outside the cluster connect on port 443.

networking:
  server:
    externalHostname: puppet.example.com
    openShiftRoute:
      enabled: true

Code from Git, as a GitHub App

Every branch of your control repo becomes a Puppet environment, deployed with g10k. Authenticate as a GitHub App, and the operator renews its short-lived tokens itself; SSH keys and HTTPS tokens work too. The operator polls Git, so no webhook has to get through your firewall.

code:
  mode: git
  git:
    authType: githubApp   # or sshKey, httpsToken
